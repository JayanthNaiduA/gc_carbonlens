1.2 What NOT to start with
Do not begin with Green Store, leaderboard, Earth Pulse or voice AI.
Do not create four independent reward implementations. All four pillars must converge on one `green_event` contract.
Do not let Gemini calculate carbon, Green Points or verification status.
Do not hard-code `$20/tree` into the engine. It is an optional sponsor policy, not a Google payment or scientific carbon value.
Do not make a separate microservice per domain for the prototype; one modular Cloud Run service is faster and easier to debug.

3. Implementation Dependency Model
3.1 Dependency rules
UI may depend on API contracts, but never on database implementation.
Domain services may use repositories/adapters; repositories must not call Gemini.
Gemini consumes normalized trusted context only; it never owns source-of-truth fields.
Reward evaluation consumes a persisted Trusted Green Event and a versioned reward policy.
Wallet balance is a projection of ledger entries; ledger history is authoritative.
BigQuery is reference/analytics truth; Firestore is low-latency operational truth.

7. Cloud Run API LLD
7.1 Prototype deployment unit
Choice:  One Cloud Run service named `carbonlens-api` containing modular domains. This minimizes deployment/debug complexity before Oct 18. Each domain exposes an internal interface so it can later become its own service.
7.2 Request middleware order
1.  Generate/propagate `request_id`.
2.  Apply request size/content-type checks.
3.  Verify Firebase ID token and derive `uid`.
4.  Verify Firebase App Check token on protected endpoints.
5.  Resolve consent requirements for the requested feature.
6.  Validate input schema and idempotency key.
7.  Execute domain service.
8.  Map domain errors to stable HTTP error envelope.
9.  Write structured access log with latency and status; exclude raw sensitive evidence.

12. Carbon Engine LLD
12.1 Input / output
CarbonEstimateRequest- subject_type: PRODUCT | TRANSPORT- category / mode- quantity + unit- region- baseline(optional)- factor_version(optional)CarbonResult- estimated_kg_co2e- avoided_kg_co2e(optional)- method- lifecycle_boundary- factor_id- factor_set_version- confidence_grade- calculation_trace[]
12.2 Product algorithm
1.  Normalize product category and quantity.
2.  Resolve active factor by category + region + effective date; fallback to global/category average if policy permits.
3.  Convert quantity to factor unit.
4.  Calculate `estimated_CO2e = normalized_quantity × kg_CO2e_per_unit`.
5.  Attach lifecycle boundary, factor provenance and confidence.
6.  Never call Gemini from this function.
12.3 Transport algorithm
baseline = distance_km * baseline_factor_kg_per_kmactual   = distance_km * actual_factor_kg_per_kmavoided  = max(0, baseline - actual)if substitution_not_proven:    avoided = null    reward_basis = "activity_only_or_none"
12.4 Failure policy
Condition
Result
No matching factor
Return `FACTOR_NOT_FOUND`; do not fabricate.
Unit incompatible
Return `UNIT_CONVERSION_ERROR`.
Factor expired and no active fallback
Return `FACTOR_VERSION_UNAVAILABLE`.
Low confidence category
Return estimate with lower confidence only if allowed; expose method.
13. Sustainability Score LLD
13.1 Scoring dimensions
score = round(  carbon_intensity * 0.40 +  reusability      * 0.20 +  packaging        * 0.15 +  recyclability    * 0.15 +  durability       * 0.10)# all component scores normalized to 0..100 where higher = better
Keep weights in versioned configuration (`score_policy_version`) so future scientific review does not rewrite history.
If a dimension is missing, use a documented missing-data rule; do not silently assume 100 or 0.
Expose both final score and component scores in API responses.
Sustainability Score is not a carbon footprint and should never be labeled “Carbon Score”.
13.2 Product replacement delta
improvement_delta = max(0, sustainable_product.score - baseline_product.score)impact_factor = min(1.0, improvement_delta / 50.0)   # demo policy example only# reward policy owns this mapping; score engine only returns the delta.

15. Reward Policy and Ledger LLD
Figure 5. Reward lifecycle state machine
15.1 Policy formula
points = round(  base_action_points  * impact_factor  * verification_factor  * confidence_factor  * persistence_factor  * anti_abuse_adjustment)points = min(points, per_event_cap, remaining_daily_cap, remaining_monthly_cap)
15.2 Policy record example
{  "version":"demo-v1",  "segment":"GROW_GREEN",  "base_action_points":100,  "verification_factors":{"V1":0.25,"V2":0.75,"V3":1.0},  "persistence":{"DAY_0":0.10,"DAY_30":0.15,"DAY_90":0.20,"DAY_180":0.25,"DAY_365":0.30},  "caps":{"per_event":5000,"daily":5000},  "sponsor": {"enabled":false,"max_currency_equivalent_per_tree":20}}
15.3 Ledger invariants
Every reward ledger entry references exactly one `event_id` and `policy_version`.
Ledger is append-only; reversals are compensating negative entries.
A unique event-to-reward guard prevents double credit.
Wallet balance must be recomputable from ledger.
Only backend service identity may create ledger entries.
Gemini, Flutter and analytics pipelines never write rewards.
16. Four Reward Pillars — Detailed Logic
16.1 Go-Green-Product
Step
Implementation
1. Capture
Product image/barcode + optional receipt.
2. Normalize
Vision/OCR → product/category resolver.
3. Baseline
Resolve conventional product/category baseline.
4. Compare
Calculate Sustainability Score delta and optional carbon difference.
5. Verify
Receipt/product evidence, same-category check, duplicate image/receipt hash.
6. Event
Create `GO_GREEN_PRODUCT` green_event.
7. Reward
Policy uses improvement delta, verification and confidence; immediate V2/V3 reward.
eligibility = (new.category == baseline.category) and (score_delta >= min_delta)if receipt_duplicate or image_reuse: rejectif evidence_level >= V2 and eligibility: evaluate_reward()
16.2 Green-Move
Step
Implementation
Baseline
User registers regular commute: origin area, destination area, normal motorized mode, typical distance.
Evidence
Health Connect activity/session + start/end time + distance; optional Maps route/location.
Plausibility
Speed bounds, overlapping trips, duplicate session IDs, unrealistic distance, time window.
Substitution
Trip must match a registered commute pattern or explicit replacement declaration.
Impact
Avoided CO2e = baseline transport - actual transport.
Reward
V2+ only for carbon-linked reward; per-trip/day caps.
Important:  A recreational walk is healthy but is not automatically avoided transport emissions. The LLD requires a credible baseline/counterfactual before carbon-linked points are issued.
16.3 Grow-Green
Checkpoint
Required implementation
State / reward

Create project; point/polygon; claimed count; species if known; fresh geo/time photo; image hash
PENDING → PROVISIONAL; small initial tranche
Day 30
Owner check-in near registered plot; fresh photo
Remain PROVISIONAL
Day 90

Additional tranche if consistent

16.3.1 Grow-Green checks
Distance from check-in location to registered plot <= policy threshold.
Media SHA-256 and perceptual similarity checks block reused images.
Timestamp must be fresh and monotonically follow previous checkpoint.
Owner cannot confirm own project as visitor.
Visitor confirmation weight decreases for repeated reciprocal confirmations.
Earth Engine Sentinel-2/vegetation data is optional plot-level corroboration; it does not prove each individual sapling.
Sponsor monetary-equivalent policy remains separate from GP and must never be described as a Google Maps payment.
16.4 Recycle-Red
Step
Implementation
1. Item intake
Photo + category + optional weight; avoid unnecessary serial numbers.
2. Document
Upload recycler receipt/certificate.
3. Extract
Document AI expense/invoice/OCR extracts recycler, date, document number, amount/weight where present.
4. Registry
Match normalized recycler against curated `verified_recyclers`.
5. Fraud
Fingerprint document; compare across users; validate date/location/category plausibility.
6. Impact
Verified diverted item category/weight; optional sourced carbon/resource benefit separately.
7. Reward
V2/V3 reward with category/weight caps.

Override deterministic fraud/verification decision
Compare known product metadata
Create unsupported claims about manufacturer/environmental impact

17.3 AI response schema
{  "summary":"...",  "why_score":"...",  "recommended_action":"...",  "alternative_product_ref":"...|null",  "confidence_note":"...",  "safety_caveat":"...|null"}

18. Vision and Document AI Processing
18.1 Product scan pipeline
1.  Client requests upload slot / creates scan id.
2.  Image uploaded to private Cloud Storage path.
3.  Backend computes content hash and checks duplicates.
4.  Vision extracts labels/text/barcode-like evidence as available.
5.  Resolver maps evidence to curated product/category; confidence is recorded.
6.  Carbon and score engines run only after normalization.
7.  Raw image follows retention policy.
18.2 Receipt / certificate pipeline
1.  Classify document purpose: purchase receipt vs recycler certificate/receipt.
2.  Send document to configured Document AI processor (Expense/Invoice/OCR depending sample format).
3.  Normalize supplier/recycler name, date, document number, total/weight/line items when available.
4.  Create normalized fingerprint from stable fields + document hash.
5.  Run duplicate and registry checks.
6.  Store extracted structured facts and processor/version metadata.
Current Google capability note:  Document AI provides pretrained Expense and Invoice parsers plus Enterprise Document OCR. Choose the processor that best matches the sample evidence and keep a fallback OCR path.
19. Pub/Sub and Asynchronous Processing
19.1 Event envelope
{  "event_type":"green_event.verified",  "event_version":"1.0",  "event_id":"evt_...",  "occurred_at":"2026-10-15T10:00:00Z",  "trace_id":"...",  "subject_ref":"green_events/evt_...",  "data": {"action_type":"GO_GREEN_PRODUCT","verification_level":"V2"}}
19.2 Topic handling rules
Consumers are idempotent by `event_id`.
Do not publish raw images, precise location or complete receipt text in Pub/Sub payloads; publish references.
Use dead-letter/retry policy for non-user-facing analytics tasks.
Reward issuance remains synchronous/transactional in the prototype; do not rely on at-least-once Pub/Sub delivery for exactly-once points.
